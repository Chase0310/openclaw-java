# 《Skills 渐进式披露对齐方案》技术评审结论

**评审对象**：`docs/skills-progressive-disclosure-alignment-plan.md`
**评审日期**：2026-04-01
**评审结论**：**有条件通过 — 补齐 6 项待定项后可进入实施**

---

## 一、方案总体判断

### 核心结论：方案思路正确，Phase A 可立即启动

本方案正确识别了 Java 与 TS 的核心差距——"正文直注入" vs "目录注入 + 按需读取"——并给出了最小侵入的改动路径（不改 runtime loop，只改 prompt 生成层）。分阶段策略合理，Phase A 作为第一步风险可控。

但方案在**预算策略、截断排序、异常处理、工具名深层映射、对话内缓存、验收可执行性**六个维度存在待定项。这些待定项中有 4 个可以通过参照 TS 源码直接收敛，剩余 2 个需要 Java 侧做出独立架构决策。

---

## 二、方案优点

### 2.1 结论先行，信息密度高

第 1 节用 6 条结论完整概括了整个方案的核心决策。阅读者不需要通读 537 行就能理解意图。这是技术文档的优秀实践。

### 2.2 差距分析精确，没有模糊地带

3.2 节 A~E 五项偏差（注入形态错误、读取时机错误、扫描目录不完整、观测面缺失、metadata 兼容不足）定位准确。每一项都有当前 Java 代码的实际行为作为对照，不是抽象的"需要改进"。

### 2.3 "不改 runtime loop" 的判断正确

方案准确识别了 Java agent loop 已经具备 tool call → 执行 → 回填 → 下一轮推理的完整闭环，渐进式披露不需要修改这个闭环，只需要改 skill 集成层。这个判断避免了大规模重构风险。

### 2.4 工具名对齐原则务实

"行为对齐 TS，提示词文案对齐 Java 实际工具名"——不搞字面照搬，确保模型收到的工具名与实际可调用的工具名一致。这是正确原则。

### 2.5 观测面设计分层合理

运行前（catalog 构建日志）、运行中（skill read trace）、API 层（`skills.status`）三级观测覆盖了主要调试场景。尤其是"模型是否真的读了 skill 文件"这条观测，是区分"注入生效"和"模型忽略"的关键信号。

## 三、待定项详析

以下 6 项待定按"能否被 TS 源码收敛"分为两类。

### A 类：可通过参照 TS 源码收敛（4 项）

这些问题的答案**已经存在于 TS 源码中**，不需要 Java 侧发明新决策，只需要读 TS 实现然后照搬。

---

#### A1. Token 预算阈值未定义

**问题描述**：方案全文多处提到"超预算"（§2.4、§4.4），但预算值本身没有定义。是按字符数还是 token 数？绝对值还是比例？硬编码还是可配置？与模型上下文窗口的关系是什么？

**收敛路径**：TS 源码中必然存在 budget 计算逻辑（可能在 prompt builder 或 skill catalog 构建模块中）。需要从 TS 代码中提取：

- 预算的计量单位（chars / tokens / 占上下文窗口百分比）
- full → compact 的触发阈值
- compact → truncation 的触发阈值
- 这些值是常量还是可配置参数

**评审要求**：实施前从 TS 源码提取具体数值，写入方案 §4.4 补充节。如果是可配置参数，给出默认值。

---

#### A2. Skill 截断排序策略缺失

**问题描述**：§4.4 提到"截断 skills 数量"，但截断顺序没有定义。是按名称字母序？按 description 长度？按 source 优先级？按最近使用频率？这个决策直接影响"哪些 skill 在紧张预算下被保留"，属于用户可感知的行为。

**收敛路径**：TS 源码中截断排序逻辑一定存在。需要提取：

- 截断时的排序 key 是什么
- 是否有 source 优先级（workspace > managed > bundled）
- 同优先级内的 tie-breaking 规则

**评审要求**：实施前从 TS 源码提取排序逻辑，写入方案 §4.4 补充节。

---

#### A3. 对话内 Skill 内容的生命周期策略缺失

**问题描述**：模型在同一对话中可能多次匹配同一个 skill。方案没有说明：是否缓存已读取的 SKILL.md 内容？如果缓存，机制是什么？长对话中 skill 内容是否会被上下文窗口挤出？

**收敛路径**：TS agent loop 的实现中，tool result 天然保留在消息历史里。需要确认 TS 是否有额外的缓存机制（如 context window 管理、skill 内容的 pinning 策略），还是纯靠消息历史自然保留。

**评审要求**：实施前确认 TS 的做法，写入方案。最可能的结果是"不额外缓存，依赖消息历史自然保留"，但必须明确写出。

---

#### A4. 异常场景处理策略缺失

**问题描述**：以下场景在方案中没有提及：

| 场景 | 未知行为 |
|---|---|
| `read_file` 指向的 skill 文件不存在 | 静默失败？返回错误给模型？ |
| skill 目录存在但 SKILL.md 为空文件 | 跳过该 skill？注入空 description？ |
| frontmatter 解析失败 | fallback 到目录名？跳过？ |
| 同名 skill 出现在多个 source | 去重？按优先级取？报错？ |
| SKILL.md 不是合法 UTF-8 | 跳过？尝试恢复？ |

**收敛路径**：TS 源码中这些边界条件一定有处理。需要从 TS 的 skill loader 和 catalog builder 中提取异常处理逻辑。

**评审要求**：实施前从 TS 源码提取异常处理策略，写入方案新增 §"异常处理与降级"。

---

### B 类：TS 源码无法收敛，需要 Java 侧独立决策（2 项）

这些问题产生的根因是 **Java runtime 与 TS runtime 的工具名体系不同**，以及 **Java 项目的测试基础设施不同**。TS 代码不会帮你解决"Java 那边的工具叫不同名字"的问题。

---

#### B1. SKILL.md 正文中工具名的深层映射问题

**问题描述**：方案 §9.2 只提了 prompt 层面的工具名对齐（`read` → `read_file`），但问题更深层：**SKILL.md 正文里写的工具指令也可能与 Java 工具名不一致**。

例如，一个为 TS 编写的 skill 正文中可能写：

```
Use the `write` tool to create the file...
Use `grep` to search for...
```

但 Java 的工具名叫 `write_file` 和 `grep_search`。这不是 prompt 层面能解决的——模型读了 skill 正文后，会尝试调用 `write`，而 Java runtime 里根本没有这个工具。

**为什么 TS 源码不能收敛**：TS 代码里写的 `write`、`grep` 就是给 TS tool registry 用的。TS 不存在"自己的工具名和 skill 正文里的工具名不一致"这个问题。

**需要 Java 侧做出的架构决策**（三选一）：

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A. 工具名映射层 | Runtime 在返回 SKILL.md 内容时，自动替换正文中的 TS 工具名为 Java 工具名 | 对 skill 作者透明，TS skill 可直接复用 | 映射维护成本，误替换风险 |
| B. Java Skill 编写规范 | 要求 Java 生态的 skill 作者使用 Java 工具名编写 SKILL.md | 实现简单，无 runtime 开销 | 生态分裂，TS skill 不能直接用 |
| C. 工具名别名注册 | Java runtime 同时注册 TS 工具名作为别名（`write` → `write_file`） | 兼容性最好 | 工具注册膨胀，歧义风险 |

**评审要求**：在方案 §9.2 中明确选择一个方向，并说明理由。推荐方案 C（别名注册），因为它的兼容性最好且不增加 skill 作者负担。

---

#### B2. 验收标准缺少可执行的测试方法

**问题描述**：§7 的验收标准是正确的定性描述，但无法直接转化为可执行的测试用例。例如：

- "模型首轮先触发 `read_file`" — 如何自动化验证？模型行为有随机性。
- compact mode 的触发条件如何构造测试数据？
- "首轮系统提示中不出现 skill 正文" — 是否有 system prompt 的 introspection 机制？

**为什么 TS 源码不能收敛**：TS 的测试基础设施（mock LLM、prompt snapshot 测试等）与 Java 项目不同。TS 的测试代码可以参考模式，但不能直接移植。

**需要 Java 侧补充的测试策略**：

| 验收项 | 建议测试方法 |
|---|---|
| §7.1 首轮注入验收 | **单元测试**：给定 mock skill 目录，断言生成的 prompt 字符串包含/不包含目标内容 |
| §7.2 命中读取验收 | **集成测试**：使用 mock LLM（预设返回 `read_file` tool_call），验证 runtime 正确传递路径并触发 trace 日志 |
| §7.3 compact 验收 | **单元测试**：构造超大量 skills，断言 prompt 进入 compact 模式并验证输出格式 |
| §7.4 兼容性验收 | **单元测试**：给定不含特殊 metadata 的 SKILL.md，断言仍能生成 catalog entry |

**评审要求**：在方案 §7 中为每个验收项补充测试方法和测试层级（单元/集成）。
